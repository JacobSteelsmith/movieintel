# Async 202 + poll serving path for MovieIntel

Adds a submit-then-poll path on the existing API Gateway v2 HTTP API to eliminate the intermittent 30s-wall `503` on the synchronous `POST /query`. A new `POST /jobs` route validates with the same strictness as `/query`, writes a `queued` job record to the existing `MovieIntel` table under a `JOB#` keyspace, async-invokes a worker Lambda (`InvocationType='Event'`), and returns `202` with a poll URL. The worker runs `run_agent` to completion, streams real per-phase progress into the record via a new backward-compatible `on_progress` callback, and writes a guaranteed terminal record. `GET /jobs/{id}` is a single fast `GetItem`. The front end moves from a single blocking fetch to submit-then-poll, and the synchronous `/query` + `/health` routes are untouched.

Watch for: nothing blocking. ## High-level view

The agent loop gained one keyword-only `on_progress` callback. Every emit is routed through an `_emit` helper that is a no-op when the callback is `None`, so a `run_agent` call without the kwarg (the synchronous `/query` path still does exactly this) is byte-for-byte identical to before. The emission points are line-anchored to the real control flow and match the design's phase/turn mapping, including the deliberate "emit nothing" branches for an invalid `final_answer` and unknown tools.

The read-path is the riskiest piece and it is handled correctly: the stored DynamoDB item carries `PK`/`SK`/`query`/`max_turns`/`expires_at` and stores no `job_id`, so `JobStore.get` never validates the raw item. It builds an explicit projected payload of only model fields, reconstructs `job_id` from the method argument, and routes `progress`/`result`/`error` through a generic `_from_dynamo` so no stray `Decimal` reaches the strict models. Every mutating write carries `attribute_exists(PK) AND status IN (queued, running)`, making terminal records final and late progress writes advisory.

The submit/worker split holds the trust boundary: the submit handler creates the `queued` record before dispatch (so a poll right after `202` always finds it), marks the job `failed` and still returns `202` if the async invoke fails, and `500`s only when it cannot even write the record. The worker owns the `queued → running` transition and wraps the run in the single allowed broad `except` that guarantees a terminal record on any crash.

The CDK adds both routes to the same HTTP API on one `SubmitFn` integration, with per-role least-privilege IAM: `SubmitFn` gets only job-item `Put/Update/Get` on the base table ARN plus `grant_invoke` on the worker — no GSI1, no `Query/Scan/BatchGetItem`, no Bedrock. `WorkerFn` mirrors the serving Bedrock/KB/DynamoDB surface plus job writes, with no `bedrock:*` and no `Resource: "*"`. Table TTL (`expires_at`) is enabled on the pipeline stack where the table is defined. All of this is locked by synth assertions and confirmed by both `cdk synth` targets.

OpenAPI documents `/query`, `/jobs`, and `/jobs/{id}` (intentionally not `/health`) and is in sync with the generator. The front end preserves the `renderResult`/`render*` textContent-only XSS boundary verbatim and only rewires `onSubmit` into submit-then-poll. Docs reflect the async flow as the recommended 503-free path with `/query` kept as the legacy fallback.

### `run_agent` is byte-for-byte identical without `on_progress`

The new parameter is `on_progress: Callable[[ProgressEvent], None] | None = None`, the last keyword-only argument. Every emission is funneled through `_emit`, which returns immediately when the callback is `None`, so no `ProgressEvent` is even constructed on the synchronous path. The serve handler calls `run_agent(...)` without the kwarg, so `POST /query` is unaffected, and `tests/agent/test_loop.py` is unchanged and passing (AC-7).

The emit sites match the design's line-anchored mapping exactly: `understanding/0` before the loop; `refused/turn+1` immediately before `safe_refusal()`; `bounded/turn+1` before the mid-loop non-`tool_use` return; per-block `searching`/`comparing`/`composing` inside the tool-dispatch loop with `composing` emitted only before returning a *valid* `final_answer`; and `bounded/max_turns` after the loop. The two "emit nothing" branches are honored and commented: an invalid `final_answer` (the `FinalAnswerError` continue) emits nothing so a stale `composing` never lingers while the loop keeps running, and an unknown tool emits nothing. A raising callback is swallowed and logged at `warning`, so progress reporting can never fail a real run.

### JobStore read-path projection and the Decimal/float round-trip

`JobStore.get` is the one place a validation `500` could sneak in, because the stored item is not a `JobStatusResponse` — it carries `PK`/`SK`/`query`/`max_turns`/`expires_at` and holds `job_id` only inside the `PK`. The implementation never calls `model_validate` on the raw item. It builds an explicit payload of `{job_id (from the argument), status, progress, created_at, updated_at}`, conditionally adds `result`/`error`, and validates that. `progress`, `result`, and `error` are each passed through `_from_dynamo`, so the nested `progress.turn` and any `pes` float come back as JSON-native numbers rather than `Decimal`.

```python
payload: dict[str, Any] = {
    "job_id": job_id,  # reconstructed from the arg, not stored
    "status": item["status"],
    "progress": _from_dynamo(item["progress"]),  # Decimal turn -> int
    "created_at": item["created_at"],
    "updated_at": item["updated_at"],
}
if "result" in item:
    payload["result"] = _from_dynamo(item["result"])  # Decimal pes -> float
```

`_to_dynamo`/`_from_dynamo` are the generic `model_dump(mode="json") -> json.dumps -> parse_float=Decimal` (and the inverse with `default=float`) pair, self-contained in `jobs_store.py` and not borrowing the movie-specific serializer. `test_jobs_store.py` locks both halves: `get(...).progress.turn == 2` and `isinstance(..., int)` after `update_progress(turn=2)`, and `get(...).result == original` for a `RecommendationList` carrying `pes=90.0` — the first use of the `AgentResult` PEP 695 alias as a Pydantic field, round-tripping losslessly via smart-union on the disjoint `kind`.

### ConditionExpression guards keep terminal records final

Every mutating method carries `attribute_exists(PK) AND #s IN (:queued,:running)`. A progress write that loses the race to a terminal mark raises `ConditionalCheckFailed`, which `update_progress` swallows at `warning` (progress is advisory). A terminal mark on an already-terminal job is likewise tolerated as an idempotent set. `create` uses `attribute_not_exists(PK)` so a duplicate id cannot clobber, and always writes a complete `understanding/0` progress map, so any readable job — including one marked `failed` by the submit handler's invoke-failure path before the worker ever ran — carries a complete `JobProgress` and never 500s the poller on a missing-`progress` validation error. `mark_running` is the sole owner of `queued → running`; `update_progress` deliberately never touches `status`.

### Submit and worker handlers hold the 202/terminal contract

Submit dispatches on `routeKey` or the resolved v2 method+path (never comparing against the `{id}` template), reusing the shared `_parse_request` so a bad body returns the structured `400` with no record and no invoke. It creates the `queued` record before invoking, so a poll immediately after `202` always finds it. A `JobStore.create` failure returns `500 submit_failed`; an async-invoke failure marks the job `failed` with `could not start worker` and still returns `202` with a pollable id. Poll resolves `{id}` from `pathParameters.id` with a last-segment fallback, returns `404` on missing/empty id or `None`, `200` on a hit (serialized with `exclude_none=True`), and `500 poll_failed` when `get` raises — matching the error-handling table and the front end's `>= 500` retry branch.

The worker reads the trusted `{job_id, query, max_turns}`, marks the job `running`, and runs `run_agent` with a `(phase, turn)`-throttled progress writer that writes on the first event or whenever the pair changes — bounding writes to roughly one per turn while keeping the user-facing turn current. The body is wrapped in the single allowed `except Exception` (`# noqa: BLE001`) that logs at `exception` and writes `mark_failed(worker_failed)`, guaranteeing a terminal record (FR-4). The generic client-facing message leaks no stack detail. `test_worker_handler.py` asserts the success path, that progress was written on `(phase, turn)` change, and that a deliberately-raising injected client yields a `failed` record with no escaped exception.

### Shared-helper refactor preserves the serve handler's test seams

`_default_bedrock_client`/`_default_kb_client`/`_default_repository`/`_decode_body`/`_bad_request`/`_decode_error`/`_parse_request` moved to `handlers/shared/serving.py`. The serve handler re-imports them into its own module namespace, so `tests/serving/test_handler.py`'s monkeypatch of `serve_module._default_*` still patches the exact names the handler calls. `test_handler.py` passes unchanged (AC-10).

### CDK routes, per-role IAM, and table TTL

Both `/jobs` routes attach to the same HTTP API via one `HttpLambdaIntegration("SubmitIntegration")`, built after the worker so `WORKER_FUNCTION_NAME` resolves. `WorkerFn` is 300s/1024MB with the full serving env and no `_sqlite` layer; `SubmitFn` is 10s/256MB with only the table/GSI/worker env. IAM is decomposed as the design pins it: `SubmitFn` gets `Put/Update/GetItem` on the base table ARN only (no GSI1, no `Query/Scan/BatchGetItem`) plus `grant_invoke` scoped to the worker ARN, and explicitly no Bedrock; `WorkerFn` gets `bedrock:InvokeModel`/`ApplyGuardrail`/`Retrieve`, the DynamoDB tool reads on table+GSI1, and job writes on the table. No statement uses `bedrock:*` or `Resource: "*"`. TTL (`expires_at`) is enabled on the table in `pipeline_stack.py` where it is defined, backward-compatibly. The extended synth tests assert the three handlers, four routes, per-role IAM shape, sizing/layers, and the TTL spec; both `cdk synth MovieIntelServingStack` and `cdk synth MovieIntelPipelineStack` emit clean templates (verified: route keys, handler strings, and `TimeToLiveSpecification: {expires_at, Enabled: true}` present).

### OpenAPI and front end

`build_openapi()` documents `POST /jobs` (202 `SubmitResponse`, 400 `ValidationErrorResponse`), `GET /jobs/{id}` (200 `JobStatusResponse` with the embedded `AgentResult` union, 404 `NotFoundResponse`, `id` path param), and keeps `/query`; `/health` stays intentionally undocumented. The on-disk `docs/openapi.yaml` is in sync (`test_on_disk_openapi_is_in_sync` passes). The embedded union is pydantic's `anyOf` smart-union rather than the hand-built `oneOf` on `/query`, which the test accepts.

The front end rewires only `onSubmit`: it POSTs `{query}` to `/jobs`, dispatches on HTTP status first (202 → poll; 400 → validation notice; 429/5xx/other → specific notices), and `pollJob` polls `GET /jobs/{id}` on a recursive `setTimeout`, branching on status first then `body.status`. Only `>= 500` and a rejected fetch are retried with linear backoff to a cap; `404`, other non-ok, `succeeded`, `failed`, and unknown `body.status` are terminal. `stopPolling` clears the single handle and re-enables the button exactly once. `renderResult` and every `render*`/`makeBadge`/`sentimentClass`/`moodClass` builder are preserved verbatim, so the textContent-only XSS boundary is unchanged; the dead `handleResponse` and fake stage timeline are removed.
